What we did

In this order, after a full backup of files and database.

  1. Back up files and database before touching anythingIf a step removes something the site needed, it can be put back. The backup also preserves the evidence.
  2. Delete files that the attacker addedBackdoors, injectors and stray scripts are not part of any release. Deleting them is safe; a clean site does not reference them.
  3. Replace WordPress core with a clean copy of the same versionCore was edited to load the attacker's code. Downloading the same release over it restores every core file without touching content, themes or plugins.
  4. Reinstall theme twentytwentyfive from wordpress.orgIts files were modified. A fresh copy of the same item replaces them all, including changes the scan did not flag.
  5. Delete settings that hold the attacker's payloadsThese are the spare copies used to rebuild the infection.
  6. Unschedule task wp_update_plugins_checkIt is registered by the malicious code and is what brings the infection back after cleanup.
  7. Delete hidden administrator wpsupportAn account the owner never created and could not see. Anything it published is handed to the owner rather than deleted.
  8. Remove invisible links from contentOnly the hidden blocks are removed; the visible text of each post stays as it was.
  9. Remove plugin simple-gallery-lite, the way inThe attacker's first change came through its "sgl_upload_image" endpoint, which accepts requests without a login. Until a fixed version exists it stays off the site.
  10. End every session and lock the doors that were usedNew salts sign everyone out, including the attacker. File editing from the dashboard is switched off, and PHP can no longer run from uploads.

What is left for you

  • Owner sets a new password; change hosting, database and email passwords. The attacker had administrator access and could have read anything stored in WordPress.
  • Keep plugins updated. This attack came in through one plugin that had not been updated; most do.
